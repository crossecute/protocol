# PR #135 edge-case audit

Reviewed on 2026-11-10 against `b0093178ec841375703153c68875a98c3b3196ad`
(`feat/signed-dispatch-108`). This follow-up targets that branch, not `main`.

## Result

Two low-severity correctness findings were reproduced and fixed, each in its own
commit with regression tests. No quorum bypass or unprivileged theft path was
confirmed in this review. This is a source review with local tests, not a formal
verification or a production-provider integration audit.

| ID | Severity | Finding | Resolution |
| --- | --- | --- | --- |
| A1 | Low | Inherited ownership renunciation bypasses the signed-mode ownership freeze | Reject renunciation in signed mode, including LayerZero's inheritance diamond; retain plain-mode behavior |
| A2 | Low | Value-bearing root registration evidence is accepted even though `registerRoot` is nonpayable | Reject nonzero signed transaction value in the shared registration decoder used by the receiver and relay builder |

## A1 — Signed ownership can be renounced

`SignedTransmitter.transferOwnership` rejects changing the fixed owner, but
OpenZeppelin's inherited `renounceOwnership` calls `_transferOwnership(0)` directly.
It never enters that override. The owner Safe could therefore renounce and
permanently disable owner-only bootstrap, send, registration and local execution.
There is no recovery setter. Receiver authority and permissionless routes remain
separate; renunciation does not revoke already signed destination authorizations.

This requires an owner-authorized source operation, so it is an operator-induced
permanent lockout, not an unprivileged takeover. The intended invariant is that
signed ownership cannot move at all.

The fix adds the same `OwnershipFixed` guard to `renounceOwnership`. LayerZero
explicitly resolves its Ownable inheritance diamond through this implementation.
Plain transmitters retain the original Ownable behavior.

Evidence: `test_signedOwnershipCannotBeRenounced` failed on the audited commit
because the expected revert did not occur, and passes after the fix. It also
bootstraps afterward to verify that the owner remains operational.
`test_plainOwnershipCanStillBeRenounced` verifies the plain-mode control.

## A2 — Impossible value-bearing registrations authorize leaves

The signed-registration decoder originally checked only calldata. A quorum-signed
Safe transaction targeting `registerRoot(root)` with `value = 1` could authorize
leaf execution through direct submission or provider delivery. The source
function is nonpayable, so that same transaction necessarily reverts there.
If the root has already been registered using valid evidence, the source relay
builder also accepted the value-bearing variant.

This does not allow forging signatures, and destinations intentionally do not
require proof of source execution. The defect is narrower: Q1.4 requires the
source call's decoding and validation rules, but the nonpayable call rule was
missing. These are malformed authorizations, rather than merely authorizations
that have not yet executed on the source.

The fix makes `SignedCalls.registeredRoot` inspect the complete `SafeTx` and reject
nonzero value before decoding its root. Both destination delivery paths and the
source quote/relay builder share it. Payable standalone sends and bootstraps are
unchanged.

Evidence: `test_aValueBearingRegistrationCannotAuthorizeALeaf` and
`test_aValueBearingRegistrationCannotBeQuotedOrRelayed` failed before the fix and
pass afterward. The source test also checks that the actual nonpayable call
rejects ETH; destination tests check both routes and unchanged execution state.

## Additional adversarial coverage

These tests exercise previously uncovered conditions without requiring another
production fix:

- `test_reentrancyAcrossAllSignedEntryRoutes`: all four outer routes (direct and
  provider standalone, direct and provider leaf) attempt nested standalone,
  leaf and finalization entry. All 12 combinations reject with the shared lock's
  exact error. A refused nested message still executes after the lock releases.
- `test_failedValueTransferRollsBackLeafAndEarlierCallsThenRetriesOnce`: a provider
  delivery executes a successful prefix, then fails for insufficient receiver ETH.
  Prefix effects, execution ID and nonce all roll back. Direct retry with funding
  succeeds, and subsequent provider duplication does not execute again.
- `test_failedStandaloneTransferLeavesDigestRetryableAcrossRoutes`: failed direct
  execution leaves the digest unconsumed; funded provider retry succeeds once and
  direct duplication does not execute again.

## Reviewed boundaries and remaining risks

The review traced authority graph validation and canonical hashing; EOA and nested
Safe signature parsing; cached child approvals; domain, target, selector and
execution-window checks; bootstrap address derivation and initialization;
standalone and leaf replay state; relay fees/refunds; provider binding inheritance;
the plain bootstrap refactor; and atomic Safe batch execution. Existing tests
cover malformed signatures, missing/duplicate approvals, altered calldata and
proofs, conflicting nonces, substituted bootstrap records and refund rejection.

The following are material design constraints already documented in #135, not
new vulnerabilities claimed or silently changed by this follow-up:

- **Signing is sufficient for destination execution.** Source guard policies,
  publication, delays and cancellation of the source Safe nonce do not revoke a
  complete destination-valid signed bundle (D19/D22 and C5/C6). Deployments must
  not treat source policy enforcement as destination authorization enforcement.
- **Authority remains the creation snapshot.** A source owner removal does not
  remove that key from an existing receiver. Rotation/counters and their retry
  semantics remain #109; key compromise requires considering stored destination
  authority, not just the live source Safe.
- **Provider gas and complete real-Safe integration remain #134.** Local signed
  conduit suites use stub Safes/guards. The separate guard suite uses real Safe
  fixtures, but that does not substitute for a complete real-Safe/guard/conduit
  integration. Deep graphs and large evidence can exceed transport gas/payload
  limits. No production gas default was recalibrated here.
- **Delivery timing remains relayer-controlled within the signed window.** A
  source-accepted leaf can fail at its destination and require retry. Synchronous
  refunds are covered; asynchronous refunds still accumulate at the transmitter.
- **Other supported limits remain:** no signed OFT mode, no signed receivers on
  diverging chains, and the governor's plain conduit must be created without a
  compatible guard. Nested Safe implementation/fallback assumptions are not
  attested by checking `getOwners` and `getThreshold` alone.
