# Authority review findings and disposition

Security review register for [#109](../safe-authority-updates.md). This file owns
finding status and unresolved choices, not duplicate design text or implementation
instructions. [Acceptance coverage](../safe-authority-verification-review.md) maps
requirements to tests. The original reviews are preserved in Git commits 9181da8
(round 1) and 5a18cd6 (round 2); superseded worksheets and the long conversation
tracker are removed from the current tree.

## Round 2

| ID | Finding | Current disposition |
| --- | --- | --- |
| Y1 | A huge signed Safe nonce can exhaust a numeric destination ordering watermark. | Addressed by linked update heads. No numeric watermark/max-gap rule; max-nonce then smaller-nonce linked handoff has a scaffold regression. Source execution divergence remains Y2, not solved by the hash. |
| Y2 | Removed old quorum can capture a lagging destination before its legitimate update arrives. | Decided: accepted, no recovery. D96 accepts stale-quorum authority and requires receiver updates before further signing. Linked heads cannot prove source execution or repair a losing branch; a destination captured by a retired quorum stays on that branch. No recovery bypass exists. Stated in the design's "Parent responsibility" section. |
| Y3 | Late destinations anchor genesis; retired keys can compete and lost lineage blocks bootstrap. | Universal update evidence and a signed activation permit replay on future chains. Decided: first accepted successor wins, with no freshness rule and no latest-state shortcut. A new destination applies the full chain from the activation, possibly in one batch. Past updates and their arguments are archived off-chain (calldata and registry events); the registry stores each Safe's selection and the graph cache only. Y7/Y8 checkpoint and graph publication work remains. |
| Y4 | Rejecting/replacing a Safe transaction on source does not revoke portable signed updates. | Decided: no expiry and no validUntil field; updates are nonexpiring as in protocol-v2#2. The destination-first model retains this consequence. Tooling must distinguish source rejection from destination revocation. The root is assumed to execute any update that has a destination quorum (see "Other decisions"); a child is not. |
| Y5 | Destination binding changes cross-chain reuse and bootstrap. | Resolved: authority updates have no destination chain/provider/registry binding. Source identity/recognized guard/domain remain authenticated. Transport and ordinary application dispatch routing stay destination-specific. |
| Y6 | Existing generic SafeBatchExecutor cannot enforce registration/mutation pairing. | Addressed by design: an ownership change is one SafeTx, a DELEGATECALL to the pinned MultiSendCallOnly whose first call is the guard's registerOwnershipChange, followed by the owner mutations. No pair, enforcing executor or pending state exists; a failure reverts the whole SafeTx and its nonce. Source template reverts until implemented. |
| Y7 | Child genesis-to-current lineage grows and missing witnesses block adoption. | A's graph stores each descendant's position, so an adoption needs child updates from that position only, not from the child's activation. A newly added or re-added Safe starts from its signed activation. Exact authenticated content cache may anchor later lineage. Specify durable full source registration evidence and checkpoint interfaces before production; no numeric evidence/depth/work cap is added. |
| Y8 | Hash-only graph storage can make execution unavailable if graph data is lost. | Draft registry stores each record once under its hash and each graph as its entry list, and reads them back by hash. Actual receiver use/publication/recovery still need integration; past updates are not recoverable from a hash. |
| Y9 | Removed signers can permissionlessly finalize accepted work before cancellation. | Accepted consequence of D92. Existing explicit cancellation remains; ownership changes are not cancellation and there is no promised cancellation priority. |
| Y10 | EIP-7702 EOA-kind owner may use a source contract signature not portable to receiver. | Guard portability validation must reject v=0 for EOA-kind owners before staging. Delegated-owner real-Safe fixture remains required. |

## Other decisions

| Topic | Decision |
| --- | --- |
| Freeze and equivocation (#109 criterion) | Rejected. No freeze leaf, equivocation-evidence submission or unfreeze role. A freeze below the selected quorum is a new authority, on a lagging destination the freezing quorum may be a retired one, and unfreezing needs a recovery role that is out of scope. Conflicting successors are handled by first-accepted. |
| Nested example (#109) | A alone updates its authority regarding its children. B has no global identity inside A and there is no default to B's state. After B rotates, A's selectAuthority carrying B's child updates is required before A dispatches under B's new owners; the issue's "A executes no transaction" wording is reconciled in the task list. |
| Other home-contract authority (DAO) | Rejected at registration; no adapter in this PR. A later one needs portable proof support, not a bridge assertion. |
| Ordered child positions | Decided. A's graph stores each descendant's position: the head hash of that Safe's own update list. A new graph keeps a position or moves it forward through that Safe's signed updates, verified against records proven from A's graph and never against the descendant's own registry entry. A height is not an identity, because a child can sign two updates after one head. |
| Whose owners vote | Decided. A descendant's signatures on an update count under the position that update names for it. The root votes under its stored record, or its creation record for an activation. Adoption never depends on a child's removed owners. |
| Removed Safe owner's vote | Decided: it does not count, for the root and child updates, on source and destinations. An update that removes a Safe owner names no position for it. Counting it under its predecessor position would need the child's predecessor graph entries in every child update, with their own proof. Removed EOA owners still vote. Removing a Safe owner whose vote is needed takes two updates: lower the threshold, then remove it. |
| Unexecuted child update | Decided: A must not adopt a child position the child signed but did not execute on source. The source guard enforces it against the set of heads the child executed, accepting any executed head at or after A's stored position. A destination cannot check execution, so there the rule is trust in A's signers. Breaking it is permanent for that child. |
| Root executes at quorum | Accepted assumption for the root only: once an update has a quorum destinations would accept, A executes it on source and does not reject or replace it. A root that breaks this is a broken multisig. A child's earlier vote counts toward that quorum even after the child rotates. |
| Adversarial child | Nothing is assumed of a child. B may sign and abandon an update or sign two at one nonce. B gains no more than its native veto: it cannot reach a destination quorum alone, and its own forked registry entry is never read for A. |
| Activation | Decided. A Safe activates the guard before any parent adds it, in a guarded transaction after setGuard: its creation quorum signs activate(initialGraphHash, creation proof). The guard requires live owners and threshold equal to the creation record and every Safe owner already activated. The initial graph names each Safe owner at its current executed position, so every destination registers the same signed graph. The activation SafeTx hash is the Safe's first head, recorded as executed, and replaces the derived genesis head. A destination registers a root from its activation through the same submitAuthority as updates, verified like an update from an empty graph; a parent adds a Safe with the activation as its first child update. A destination cannot see execution; the unexecuted-update rule covers it. |
| Removed and re-added Safe | Decided. Treated as an added Safe: it starts from its activation, and any executed position may be named, including one earlier than where it was removed. A Safe's executed heads form one list, so any of them still leads to its later positions. |
| Creation proof | Decided. SafeCreationProof {singleton, initializer, saltNonce}. The factory and proxy initcode are compiled-in pins (see Registry pins), so the proof does not carry them; the singleton must be Safe or SafeL2. The Safe address is recomputed with both Safe 1.5.0 salts (plain and chain-specific); a match on either proves the initializer. The initializer is setup with to/data empty or exactly SafeToL2Setup.setupToL2 with the pinned L2 singleton. Owners and threshold come from the initializer, kinds from the graph. |
| Nested voters in child updates | Decided. A Safe owner C voting inside B's update counts under the position B's new graph names for C, as on source. childUpdates is one flat list of child updates at any depth, checked once in order against a table of proven (Safe, position) records seeded from A's stored entries and added Safes' activations. Each child update carries its new record and its new graph's entries. A retained Safe's new position must descend from its stored one. Counting C under A's record instead can permanently block adopting an executed B update. |
| One-transaction ownership change | Decided. Registration and mutation merge into one SafeTx: DELEGATECALL to the pinned MultiSendCallOnly, first calling guard.registerOwnershipChange(update), then the owner self-calls. Removes the nonce m/m+1 pair, the enforcing executor and the pending lock (Y6, X2) and one signing round. |
| Staging channel | Decided. stageUpdate(sourceSafe, newGraph, childUpdates, portableSignatures, nestedApprovals) in the same outer transaction, held in transient storage for the Safe's next guarded transaction. Not appended to Safe's signatures: the policy engine's context extension already uses that tail and its format allows one extension per blob. The guard emits portableSignatures and nestedApprovals; destinations receive them with newGraph and childUpdates. |
| Encoding simplifications | Decided, each at no security cost: no rootSafe field (nodes[0] is the root and its record hash commits to it); no previousAuthorityHash (previousUpdateHash already commits to the previous graph); no factory field in the creation proof; activate(authorityHash, creation) without zero predecessors; one submitAuthority for activations and updates. portableSignatures is always supplied, with no empty shortcut, so it never carries the policy context extension. Records and positions travel as AuthorityNode, so no parallel arrays. |
| Execution path | Decided. Updates execute through our tooling as multicall([stageUpdate, execTransaction]) via any multicall contract, unpinned: the multicall holds no invariant, the single SafeTx makes registration and mutation atomic and the guard enforces every check. Owners can sign in the Safe UI, but its plain execTransaction reverts because nothing is staged. SafeBatchExecutor cannot serve, as it only calls execTransaction. |
| Graph hash and storage | Decided. The graph hash covers (recordHash, position) per Safe; each record is stored once under its hash and each graph as its entry list, so an update writes only changed records. |
| Migration from #108 fixed authority | None. Nothing from #108 is deployed; receivers adopt the shared registry directly. |
| Stored cycles | Decided: rejected, with #108's SafeAuthorityGraph rule and traversal. The guard checks every activation and update graph on source and the registry on destinations, with stored owner kinds. Stored graphs therefore never hold a cycle; a live source cycle only blocks the adoption that would store it. Supersedes the "permits stored cycles" wording added in 24b7f7f. |
| Undeployed owner address | Decided: an owner added with no code is EOA-kind and stays so after a Safe is deployed there, until its Safe removes or swaps it out; its contract signatures never count (Y10). Not a security issue: the portable check runs on source too, so source and destinations agree. The guard cannot distinguish it from an EOA; tooling should warn. No guard check on EOA-kind owners with code. |
| Re-added owner kind | Decided. An owner removed and added again, even within one ownership batch, takes the kind the new record names. An owner that stays keeps its kind. A Safe-kind owner still needs a proven position. |
| Unused or repeated child updates | Decided: rejected on source and destinations by the shared check. Every supplied child update must be used, by the new graph or as a later child update's predecessor or voter, and none may repeat. A child update that re-proves a position already proven, such as a stored one, counts as a repeat. Independent child updates may still come in any valid order. |
| Child update record | Decided. A child update carries the child's full new record next to its new graph's entries, and the entries are never empty. The first entry's record hash must equal the record's hash, and the entries must hash to the graph hash the child signs. The verifier checks the record against the update: an ownership change must turn the predecessor record into it (applyMutations), an activation must match the creation proof's owners and threshold, and a selectAuthority must keep the predecessor record. The kinds of added and creation owners come from it, bound by the child's signatures (Y10). Cost: 32 x (5 + 2n) bytes per child update for an n-owner child, 992 for a 13-owner child; a hashes-only list of added owners' kinds would cost about half, with a split derivation. |
| Registry verification layout | Decided. The registry template implements graph authentication itself: the canonical check and 16-owner cap, the root record per update kind, the flat child-update pass and the strict use and repeat checks. One hook remains: source-call recognition, which returns the update kind, the signed update and the decoded mutations or creation proof. One vote check in the template serves the root and every child update, and it resolves nested Safe voters through the table of proven positions under the positions the voting update's new graph names. |
| Shared signature walk | Decided. The vote check and #108's receiver run one Safe 1.5.0 signature walk (SafeQuorum). It reads each Safe's threshold and owner membership through two lookups: stored owner lists for the receiver, and for the registry the voting Safe's record plus the table of proven positions. The receiver keeps its storage reads. SafeAuthority's bytecode changes and its receiver gas moves by at most 0.25% in SignedDispatchGas; no other artifact changes. The source collector stays separate: it checks format only and fetches approvals from the guard. A memory verifier beside the stored one would have duplicated the threshold, ordering, kind and nested rules. |
| Unused nested approvals | Decided: ignored, as in #108; duplicates for one child and message reject. An unused approval is never counted or stored and the update head does not cover evidence. Rejecting it would not make evidence unique, since a signature blob can carry unread bytes, and would need the shared walk to track use. |
| Zero creation threshold | Decided: the creation proof check rejects it, on source and destinations. Safe's setup refuses a zero threshold, but a creation proof shows an address, not a deployment, so a child activation with one would otherwise need no signatures. The signature walk also refuses a zero threshold. A threshold above the owner count, a duplicate owner and a zero owner are not checked: none can form a quorum. |
| Registry pins | Decided: compiled in, with no writer and no key. The guard and the registry hold Safe 1.5.0's canonical factory, Safe and SafeL2 singletons, SafeToL2Setup and MultiSendCallOnly, the two proxy initcode hashes (one per singleton) and the guard's address as constants, the same for every source chain. safe-deployments lists one address set for 1.5.0 on all 141 of its networks (checked 2026-11-15); the proxy creation code was read from the mainnet factory. The registry takes no constructor arguments, so it deploys through Arachnid's factory at one address on every standard EVM chain and needs no deployer record; receivers use that address. A chain without the canonical set, or a new guard, needs a new registry generation (X13). A key that wrote pins could, once stolen, pin a fake factory for an unpinned source chain and forge creation proofs. |
| Two signature sets on source | Decided. Safe's check counts live child owners; the guard's portable check is the destination check. When a child rotates between its vote and A's quorum, live owners execute and the earlier set is handed to the guard outside the signed SafeTx. The guard must verify and emit it. |

## Decision lineage

D79 keeps registration/mutation atomic, now as one SafeTx, D87 fixes 16 immediate owners without an
aggregate cap, D90 makes the root control its selected descendants, D91 chooses
Safe-scoped shared selections, D92 preserves accepted commitments, D94/D96 assign
freshness responsibility to A, and D95 adds no depth/evidence/work caps.
D93 numeric nonce ordering is superseded by the linked-head design. The paused
2^16 forward-gap proposal was not adopted. Final interface discussion selects
universal source-signed evidence, guard operations for activation, ownership change
and selection, one-SafeTx ownership batches through pinned MultiSendCallOnly, and a
zero-hash sentinel, now signed by the activation. Historical
global authority/counter/pinning and implicit-child-adoption alternatives are not
active requirements.
