# Authority review findings and disposition

Security review register for [#109](../safe-authority-updates.md). This file owns
finding status and unresolved choices, not duplicate design text or implementation
instructions. [Acceptance coverage](../safe-authority-verification-review.md) maps
requirements to tests. The original reviews are preserved in Git commits 9181da8
(round 1) and 5a18cd6 (round 2); superseded worksheets and the long conversation
tracker are removed from the current tree.

## Round 2

| ID | Finding | Current disposition |
| --- | --- | --- |
| Y1 | A huge signed Safe nonce can exhaust a numeric destination ordering watermark. | Addressed by linked update heads. No numeric watermark/max-gap rule; max-nonce then smaller-nonce linked handoff is covered by ReceiverAuthorityTemplate.testHugeSignedNonceDoesNotBlockLinkedLowerNonce. Source execution divergence remains Y2, not solved by the hash. |
| Y2 | Removed old quorum can capture a lagging destination before its legitimate update arrives. | Decided: accepted, no recovery. D96 accepts stale-quorum authority and requires receiver updates before further signing. Linked heads cannot prove source execution or repair a losing branch; a destination captured by a retired quorum stays on that branch. No recovery bypass exists. Stated in the design's "Parent responsibility" section. |
| Y3 | Late destinations anchor genesis; retired keys can compete and lost lineage blocks bootstrap. | Resolved (#148): a receiver starts from the head and selected graph its bootstrap carried, on the provider's authentication, so a late destination needs no past updates and a retired quorum can neither seed nor pre-empt it. Successors of that head: first accepted wins, with no freshness rule. Past updates and their arguments are available in source calldata and guard events for off-chain archives serving lagging receivers. Full source submissions are published for transport and archival. The [archive utility](../../tools/authority-archive/README.md) retrieves graph witnesses and forward catch-up evidence; operators still need finalized capture and independent persistent copies (Y7/Y8). |
| Y4 | Rejecting/replacing a Safe transaction on source does not revoke portable signed updates. | Decided: no expiry and no validUntil field; updates are nonexpiring as in protocol-v2#2. The destination-first model retains this consequence. Tooling must distinguish source rejection from destination revocation. The root is assumed to execute any update that has a destination quorum (see "Other decisions"); a child is not. |
| Y5 | Destination binding changes cross-chain reuse and bootstrap. | Resolved: authority updates have no destination chain/provider/receiver binding. Source identity/recognized guard/domain remain authenticated. Transport and ordinary application dispatch routing stay destination-specific. |
| Y6 | Existing generic SafeBatchExecutor cannot enforce registration/mutation pairing. | Implemented: an ownership change is one SafeTx, a DELEGATECALL to the pinned MultiSendCallOnly whose first call is the guard's registerOwnershipChange, followed by owner mutations. No pair, enforcing executor or pending state exists; failure reverts the whole SafeTx and its nonce. |
| Y7 | Child genesis-to-current lineage grows and missing witnesses block adoption. | A's selected graph commits to each descendant's position, so an adoption needs forward child updates from that position only. Source callers must supply that full current graph from staging calldata, published submissions or their archives; the guard authenticates it against the selected hash. Intermediate proof positions and historical receiver caches are not reusable checkpoints. Later positions may repeat earlier owners but need their own forward links. Added/re-added Safes are named directly by the root. The archive utility detects missing links and retrieves complete forward chains; its tests restore a missing prefix. Operating finalized evidence capture and independent backups remains required. No numeric evidence/depth/work cap is added. |
| Y8 | Hash-only graph storage can make execution unavailable if graph data is lost. | Source storage contains only selection, executed-head record and publication hashes; full source graphs must be preserved externally from staging calldata and full submission events. Receivers store full records and graph entries for ordinary signer verification. The archive utility imports graphs against selected hashes and recovers witnesses from backed-up copies, including activation graphs. ABI encoding/decoding runs in process and hashing streams through stdin, so evidence does not depend on process-argument size limits. Regressions recover a 66,240-byte graph and a signed submission larger than 128 KiB. Operators must preserve independent copies and test restoration. A hash cannot reconstruct missing data or authorize traversal from an old position. |
| Y9 | Removed signers can permissionlessly finalize accepted work before cancellation. | Accepted consequence of D92. Existing explicit cancellation remains; ownership changes are not cancellation and there is no promised cancellation priority. |
| Y10 | EIP-7702 EOA-kind owner may use a source contract signature not portable to receiver. | Implemented: the guard rejects v=0 for EOA-kind owners before execution. AuthorityDelegatedOwner.t.sol uses a real Prague delegation and Safe 1.5.0: its contract signature passes native Safe validation but fails portable validation, while ECDSA succeeds. Compiler settings stay Cancun. |

## Round 1 retained items

| IDs | Status |
| --- | --- |
| X1 | Portable signature validation remains mandatory in the pre-hook, before the update executes on source. |
| X2 | Addressed with Y6: registration and mutation are one SafeTx, so no registration can wait for its mutation. |
| X3/X5/X8/X9/X12 | Former global-history/refresh/counter mechanisms removed; no such active requirements remain. |
| X4/X14 | The root authenticates an update under its stored record; each descendant votes under the position the update names, proven by child updates from the stored position. Lagging/new-chain risks are Y2/Y3 and accepted snapshot staleness is D94/D96. |
| X6/X7 | Old commitment invalidation questions superseded by D92 permanent accepted authorization subject to explicit cancellation/consumption. |
| X10 | Same-Safe nested execution/staging overwrite. Implemented: every owner execution holds a per-Safe lock that rejects stageUpdate and same-Safe owner or guarded module reentry until its matching post-hook, and staged data is consumed by one transaction. |
| X11 | Activation must name/verify singleton, both guards, handler and enabled modules; slot installation alone is insufficient. Implemented at activation: both slots hold the guard, the singleton and handler are pinned, and no module is enabled; self-calls are refused afterwards, so none can be enabled later. |
| X13 | Default/helper/configuration governance must not gain an unreviewed way to replace authenticated owner authority. Decided: helper, singleton and handler pins are fixed at guard deployment, with no setter and no owner or governance override. Changing one means a new guard; guard migration is out of scope. Enforced through constructor immutables. No executor pin: with the one-transaction ownership change no executor holds an invariant. |

## Other decisions

| Topic | Decision |
| --- | --- |
| Child transition proofs | A retained child stays at its stored position or moves through valid forward links supplied with the update. Intermediate positions are scoped to that verification, with no checkpoint reuse or backward traversal through cached authority. A later position may repeat an earlier owner record, including its threshold, but has its own authenticated update head. |
| Pre-activation restrictions | Implemented: ordinary calls remain policy-controlled, subject to the per-Safe owner-execution lock. The pinned MultiSend executor is restricted to recognized authority-change batches before and after activation; module batches reject. Explicit activation reads live state. |
| Freeze and equivocation (#109 criterion) | Rejected. No freeze leaf, equivocation-evidence submission or unfreeze role. A freeze below the selected quorum is a new authority, on a lagging destination the freezing quorum may be a retired one, and unfreezing needs a recovery role that is out of scope. Conflicting successors are handled by first-accepted. |
| Nested example (#109) | A alone updates its authority regarding its children. B has no global identity inside A and there is no default to B's state. After B rotates, A's selectAuthority carrying B's child updates is required before A dispatches under B's new owners; issue #109 now states explicit parent adoption, with a real-Safe end-to-end regression. |
| Other home-contract authority (DAO) | No signed mode; no adapter in this PR. A later one needs portable proof support, not a bridge assertion. |
| Ordered child positions | Decided. A's graph stores each descendant's position: the head hash of that Safe's own update list. A new graph keeps a position or moves it forward through that Safe's signed updates, verified against records proven from A's graph and never against the descendant's own receivers' state. A height is not an identity, because a child can sign two updates after one head. |
| Whose owners vote | Decided. A descendant's signatures on an update count under the position that update names for it. The root votes under its stored record. Adoption never depends on a child's removed owners. |
| Removed Safe owner's vote | Decided: it does not count, for the root and child updates, on source and destinations. An update that removes a Safe owner names no position for it. Counting it under its predecessor position would need the child's predecessor graph entries in every child update, with their own proof. Removed EOA owners still vote. Removing a Safe owner whose vote is needed takes two updates: lower the threshold, then remove it. |
| Unexecuted child update | Decided: A must not adopt a child position the child signed but did not execute on source. The source guard enforces it against the set of heads the child executed, accepting any executed head at or after A's stored position. A destination cannot check execution, so there the rule is trust in A's signers. Breaking it is permanent for that child. |
| Root executes at quorum | Accepted assumption for the root only: once an update has a quorum destinations would accept, A executes it on source and does not reject or replace it. A root that breaks this is a broken multisig. A child's earlier vote counts toward that quorum even after the child rotates. |
| Adversarial child | Nothing is assumed of a child. B may sign and abandon an update or sign two at one nonce. B gains no more than its native veto: it cannot reach a destination quorum alone, and its own receivers' state is never read for A. |
| Activation | Decided. A Safe activates the guard before any parent adds it and before its first signed bootstrap, in a guarded transaction after setGuard: its quorum signs activate(initialGraphHash). The guard requires the root record equal to the live owners and threshold and every Safe owner already activated, so a Safe that has changed owners since creation can activate. The initial graph names each Safe owner at an executed position with its record there, including an earlier executed position; live and portable signature sets may differ. The activation SafeTx hash is the Safe's first head, recorded as executed. No creation proof (#148): destinations never receive an activation, since a receiver starts from the head and graph its bootstrap carries. |
| Removed and re-added Safe | Decided. Treated as an added Safe: the new graph names its record and position, and any executed position may be named, including one earlier than where it was removed. A Safe's executed heads form one list, so any of them still leads to its later positions. |
| Added Safes | Decided (#148): no creation proofs. A Safe a new graph adds is taken as named, on the root's signers; the source guard requires the named position to be one that Safe executed and the record to be its record there. An added Safe cannot vote on the update that adds it. Retained descendants still move only through their own child updates. |
| Nested voters in child updates | Decided. A Safe owner C voting inside B's update counts under the position B's new graph names for C, as on source. childUpdates is one flat list of child updates at any depth, checked once in order against a table of proven (Safe, position) records seeded from A's stored entries. Each child update carries its new record and its new graph's entries. A retained Safe's new position must descend from its stored one. Positions are proven only forward from A's stored ones (#148), so a B update whose voter C sits behind A's stored position for C cannot be adopted; B signs a fresh update under C's current owners, or A removes B and adds it again at the named position. |
| One-transaction ownership change | Decided. Registration and mutation merge into one SafeTx: DELEGATECALL to the pinned MultiSendCallOnly, first calling guard.registerOwnershipChange(update), then the owner self-calls. Removes the nonce m/m+1 pair, the enforcing executor and the pending lock (Y6, X2) and one signing round. |
| Staging channel | Decided. stageUpdate(sourceSafe, currentGraph, newGraph, childUpdates, portableSignatures, nestedApprovals) in the same outer transaction, held in transient storage for the Safe's next guarded transaction. The guard authenticates currentGraph against its stored selection hash before using its records; activation does not use it. Not appended to Safe's signatures: the policy engine's context extension already uses that tail and its format allows one extension per blob. The guard emits portableSignatures and nestedApprovals; destinations receive them with newGraph and childUpdates. |
| Encoding simplifications | Decided, each at no security cost: no rootSafe field (nodes[0] is the root and its record hash commits to it); no previousAuthorityHash (previousUpdateHash already commits to the previous graph); activate(authorityHash) without zero predecessors; one receiver entry point for updates. portableSignatures is always supplied separately, with no empty shortcut and no implicit copy of the execution blob. The guard verifies and publishes the supplied bytes; unused trailing bytes grant no authority. Records and positions travel as AuthorityNode, so no parallel arrays. |
| Execution path | Decided. Updates execute through our tooling as multicall([stageUpdate, execTransaction]) via any multicall contract, unpinned: the multicall holds no invariant, the single SafeTx makes registration and mutation atomic and the guard enforces every check. Owners can sign in the Safe UI, but its plain execTransaction reverts because nothing is staged. SafeBatchExecutor cannot serve, as it only calls execTransaction. |
| Graph hash and storage | Decided. The graph hash covers (recordHash, position) per Safe. The source guard keeps only selection, executed-head record and publication hashes, with full graphs supplied in staging calldata and published submissions. Receivers store each record once under its hash and each graph as its entry list, so updates write only changed records and ordinary messages need no authority witness. Both paths share transition and quorum verification. |
| Migration from #108 fixed authority | None. Nothing from #108 is deployed; receivers hold their authority directly. |
| Stored cycles | Decided: rejected, with #108's SafeAuthorityGraph rule and traversal. The guard checks every activation and update graph on source and every receiver checks it, with stored owner kinds. Stored graphs therefore never hold a cycle; a live source cycle only blocks the adoption that would store it. |
| Undeployed owner address | Decided: an owner added with no code is EOA-kind and stays so after a Safe is deployed there, until its Safe removes or swaps it out; its contract signatures never count (Y10). Not a security issue: the portable check runs on source too, so source and destinations agree. The guard cannot distinguish it from an EOA; tooling should warn. No guard check on EOA-kind owners with code. |
| Re-added owner kind | Decided. An owner removed and added again, even within one ownership batch, takes the kind the new record names. An owner that stays keeps its kind. A Safe-kind owner still needs a proven position. |
| Unused or repeated child updates | Decided: rejected on source and destinations by the shared check. Every supplied child update must be used, by the new graph or as a later child update's predecessor or voter, and none may repeat. A child update that re-proves a position already proven, such as a stored one, counts as a repeat. Independent child updates may still come in any valid order. |
| Child update record | Decided. A child update carries the child's full new record next to its new graph's entries, and the entries are never empty. The first entry's record hash must equal the record's hash, and the entries must hash to the graph hash the child signs. The verifier checks the record against the update: an ownership change must turn the predecessor record into it (applyMutations), and a selectAuthority must keep the predecessor record. The kinds of added owners come from it, bound by the child's signatures (Y10). Cost: 32 x (5 + 2n) bytes per child update for an n-owner child, 992 for a 13-owner child; a hashes-only list of added owners' kinds would cost about half, with a split derivation. |
| Receiver verification layout | Decided. The receiver authority library implements graph authentication itself: the canonical check and 16-owner cap, the root record per update kind, the flat child-update pass and the strict use and repeat checks. AuthorityRecognition is the source-call recognizer shared by the source guard and concrete receivers; it returns the update kind, signed update and decoded mutations against the configured pins. One vote check serves the root and every child update, and it resolves nested Safe voters through the table of proven positions under the positions the voting update's new graph names. |
| Shared signature walk | Decided. The vote check and #108's receiver run one Safe 1.5.0 signature walk (SafeQuorum). It reads each Safe's threshold and owner membership through two lookups: stored owner lists for dispatch, and for update verification the voting Safe's record plus the table of proven positions. The receiver keeps its storage reads. At the signature-walk extraction in 26eadff, SafeAuthority's bytecode changed and its receiver gas moved by at most 0.25% in SignedDispatchGas. Current receiver/source integration measurements are tracked separately in the benchmark report. The source collector stays separate: it checks format only and fetches approvals from the guard. A memory verifier beside the stored one would have duplicated the threshold, ordering, kind and nested rules. |
| Unused nested approvals | Decided: ignored, as in #108; duplicates for one child and message reject. An unused approval is never counted or stored and the update head does not cover evidence. Rejecting it would not make evidence unique, since a signature blob can carry unread bytes, and would need the shared walk to track use. |
| Destination pins | Constructor immutables, with no setter: Safe 1.5.0's MultiSendCallOnly address and the source guard address. Bootstrap names its source guard and must match that pin. Both pins unset permit plain mode only. No registry contract and no factory, singleton, SafeToL2Setup or proxy initcode pins (#148). Changing a pin needs a new receiver implementation (X13). |
| Pre-emptive capture | Decided (#148): authority is per receiver, seeded by the bootstrap's head and selected graph. No shared registry and no registration from the public activation, so a retired creation quorum cannot seed or drive a receiver. The bootstrap trusts the provider and source transceiver. |
| Two signature sets on source | Decided. Safe's check counts live child owners; the guard's portable check is the destination check. When a child rotates between its vote and A's quorum, live owners execute and the earlier set is handed to the guard outside the signed SafeTx. The guard must verify and emit it. |
| Automatic activation | Evaluated and not adopted (#148): the guard would derive the initial graph, so a Safe owner that has not activated would block an unrelated transaction or be recorded EOA-kind, and the first head would be an arbitrary transaction's hash. A signed activation costs one transaction and keeps the graph the owners' statement. |

## Decision lineage

D79 keeps registration/mutation atomic, now as one SafeTx, D87 fixes 16 immediate owners without an
aggregate cap, D90 makes the root control its selected descendants, D91 scopes
selections to the source Safe, held per receiver, D92 preserves accepted commitments, D94/D96 assign
freshness responsibility to A, and D95 adds no depth/evidence/work caps.
D93 numeric nonce ordering is superseded by the linked-head design. The paused
2^16 forward-gap proposal was not adopted. Final interface discussion selects
universal source-signed evidence, guard operations for activation, ownership change
and selection, one-SafeTx ownership batches through pinned MultiSendCallOnly, and a
zero-hash sentinel, now signed by the activation. Historical
global authority/counter/pinning and implicit-child-adoption alternatives are not
active requirements.
